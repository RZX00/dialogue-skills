# 概念命名

## 1 范围

本技能适用于 Agent 为项目中会被反复使用的概念命名、撰写定义、检查名称一致性，以及维护项目术语表。

## 2 术语和定义

2.1 术语卡：为单个概念起草、交由用户确定的命名记录。

2.2 术语表 glossary：一个项目内已确定名称的集合。

2.3 限界上下文 bounded context：一个模型被定义并适用的边界（Evans 2015）。本技能中，一个项目即一个限界上下文；同一词语在两个项目中可指称不同对象。

2.4 规定性定义 stipulative definition：约定一个词语在特定语境中如何使用的定义，只有适用与否，没有真假（Robinson 1950）。术语卡中的定义均属此类。

2.5 内涵定义 intensional definition：写出概念最近的上位概念及其区别特征的定义，即属加种差（ISO 704:2022）。

## 3 原则

一个名称被一个群体接受后，即成为该群体的约定，此后的陈述与行动均以此为准。因此名称应在确定前审慎选择，确定后保持不变；确需更改的，应视同设计变更，明确宣布。

## 4 一致性检查

4.1 同一律：一个对象应只有一个名称，一个名称应只指称一个对象。Agent 发现两个名称指称同一对象，或一个名称指称两个对象时，应予指出，并请用户确定一个名称。

4.2 矛盾律：同一概念的两处表述不应互相否定。Agent 发现冲突时，应列出两处原文，请用户确定以哪一处为准。

4.3 排中律：对于任一对象，应能判定其属于或不属于该概念。定义无法判定边界情形时，应补充一个正例和一个反例，或以可测量的阈值加以规定（操作性定义，Bridgman 1927）。

## 5 起草术语卡

5.1 当一个新概念将被反复使用时，Agent 应起草术语卡，交由用户确定。术语卡包含下列各项：

| 项 | 要求 |
|---|---|
| 正式名 | 应优先采用现成术语，查阅 `references/concepts.md` 第三部分；无合适的现成术语时，方可另起名称，并说明现成术语不适用的原因 |
| 定义 | 内涵定义，一句话写明上位概念和区别特征 |
| 正例 | 一个典型实例 |
| 反例 | 一个最易混淆的实例，并写明区别 |
| 近义术语 | 现有术语中与其最接近的一个，并写明区别 |
| 停用名称 | 确定正式名后不再使用的同义名称 |

5.2 互相引用的一组核心概念（例如身份、消息、对话、会话）应合并为一段定义：先写明各概念之间的关系，再分别下定义，定义中可直接引用组内其他概念（隐定义，Hilbert 1899）。

## 6 术语表

6.1 用户确定名称后，Agent 应将其写入术语表。术语表为 Markdown 表格，表头为 `| 正式名 | 定义 | 正例 | 反例 | 停用名称 | 确定日期 |`。

6.2 术语表的位置依次为项目的 `docs/glossary.md`、项目根目录的 `GLOSSARY.md`；两者均不存在时，应新建 `docs/glossary.md`。

## 7 名称检查

7.1 Agent 撰写或修改文档后，宜运行 `node scripts/term-check.mjs --file <路径>`（或 `--text "<文本>"`）。该脚本列出文本中使用了术语表「停用名称」的位置，引号内的提及不计。

7.2 已安装 Stop 钩子时，上述检查在每次答复结束后自动执行，Agent 不必另行运行。

## 8 示例

<examples>
<example>
用户：文档里有人写 room，有人写房间，有人写群，统一一下。
Agent：先确认三个名称是否指称同一对象。若是，起草术语卡：正式名「对话」；定义「多个身份共用、仅可追加的消息记录」；正例：三个人与两个 Agent 讨论接口的消息序列；反例：某个 Agent 的一次运行，属于「会话」；停用名称：room、房间、群。交由用户确定后写入术语表。
</example>
<example>
用户：我们说的活跃用户怎么定义比较好？
Agent：「活跃」包含两个未界定的维度：行为类型与时间窗口。给出两个操作性定义供用户选择：「过去 7 天内发送过至少一条消息」或「过去 7 天内完成过至少一次交接」，并说明二者各自纳入和排除的用户类型。
</example>
</examples>
