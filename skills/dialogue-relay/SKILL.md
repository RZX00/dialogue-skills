# 代理转述

## 1 范围

本技能适用于两类情形：Agent 代表用户向第三方（人或其他 Agent）传达信息、委派任务；Agent 依据第三方转来的信息采取行动。

## 2 术语和定义

2.1 转述 relay：Agent 将用户的意图传达给第三方的行为。

2.2 接收方 recipient：转述所指向的人或 Agent。

2.3 承诺内容 commitment：说话人通过断言所承担的责任，即认定该断言为真并能为其提供理由（Brandom 1994）。

2.4 共同背景 common ground：对话双方都接受、并且都知道对方接受的前提（Stalnaker 2002）。

2.5 事务类话语：告知、请求、委派、承诺和拒绝。

2.6 表达类话语 expressive：表露说话人态度的话语，如道歉、致谢、婉拒、催促和抱怨（Searle 1975）。

2.7 回述 back-brief：任务接收方向任务发出方说明自己拟如何执行该任务（美军 FM 6-0）。

## 3 合格标准

接收方依据转述所采取的行动，应与用户直接向其陈述时所采取的行动一致。

注：意义由接收方依据自身已有的知识重建（Reddy 1979），而接收方不具备用户与 Agent 之间的共同背景。因此转述应同时满足两项要求：承诺内容保持不变；接收方缺失的背景予以补足。

## 4 发出转述前的要求

4.1 话语分类：Agent 应首先判定待转述内容属于事务类话语还是表达类话语。

4.2 表达类话语：Agent 应转达用户原话，保留原话的模糊程度和语气，不应附加对任何人动机或情绪的推测。代为转达的道歉和致谢应注明「代转」。用户未提供原话时，Agent 应向用户索取，不应自行撰写。

注：间接表达为双方在关系上保留了回旋余地（Pinker, Nowak & Lee 2008）；由 Agent 撰写的道歉不付出任何代价，属于廉价表态（cheap talk，Crawford & Sobel 1982），接收方不会据此调整判断。

4.3 承诺内容不变：事务类话语的下列五项应与用户原话一致。
- a) 规范强度：「最好」不应转为「必须」，「宜」不应转为「应」。
- b) 信息来源：用户原话、用户的估计和 Agent 的推断应分别标注。
- c) 量化范围：「有两个用户」不应转为「用户」。
- d) 条件关系：「若 X 则做」不应转为「仅当 X 才做」，也不应省略条件。注：将充分条件理解为充要条件的倾向称为条件完美化（Geis & Zwicky 1971）。
- e) 例外条件：「除非……」应随主张一并转达。

4.4 目的说明：转述任务时，应说明用户使用该结果的目的（指挥官意图，ADP 6-0）。注：接收方遇到未预见的情形时，依据目的调整执行方式。

4.5 补充背景的可追溯性：Agent 补充的每一项背景，应可追溯至用户的原话、既有决定或已定术语；无法追溯的，应标注「用户未说明」。用户未说明的事项可能是有意交由接收方决定的；无法判断时，Agent 应向用户确认该事项由接收方决定还是另有要求，不应代为补充。

4.6 术语转换：将用户的内部用语替换为接收方熟悉的用语时，应在括号中注明用户的原用语。

4.7 非转述内容：用户对 Agent 的抱怨、试探和尚未确定的想法，未经用户授权不应转述。

## 5 接收转述时的要求

5.1 归属标注：第三方的断言应归属于其说话人，表述为「某某称……（未核实）」；经核实后，方可去除归属。注：听者对断言可以接受（视为自己的承诺），也可以仅将其归属于说话人（Brandom 1994）。

5.2 回述：据转述采取行动前，Agent 应先向对方说明拟执行的动作及其终止点，随后执行，不必等待答复。Agent 不应仅逐字复述对方的请求：逐字复述只能发现听取错误，无法发现理解错误。

5.3 澄清：仅当转述内容存在两种以上会导致不同行动的解释时，Agent 才应向对方澄清，并以一次为限。

## 6 示例

<examples>
<example>
用户：有两个用户问过能不能导出 CSV，这周排得开就做一个。
不符合（量化范围和条件关系均被改变）：用户需要导出 CSV，这周做一下。
符合：用户称有两个用户询问过 CSV 导出。本周排期允许则做，不允许可以不做；用户未要求本周完成。
</example>
<example>
用户：跟她说这周可能排不过来，看看下周？
不符合（将婉拒改写为确定的拒绝）：他这周不做，下周再说。
符合：他说这周可能排不过来，问下周是否可以。
</example>
<example>
用户：老周那单这周接不了，烦死了，他们老改需求。
不符合（道歉为 Agent 自行撰写，抱怨被作为理由转出）：非常抱歉，我们这周无法承接，原因是贵方需求变动较频繁。
符合：用户原话：「这单这周接不了。」原因用户未授权转达，如有需要我可以向他确认。
</example>
<example>
用户：让设计那边做成插件，别碰内核。
符合：请做成可单独安装、卸载后不影响主程序的扩展（用户原用语为「插件」），主程序本身不作修改（用户原用语为「内核」）。目的：下周供外部开发者试装。
</example>
<example>
收到 A 的 Agent：接口昨天改成 v2 了，你们那边把调用换一下。
回述给 A 的 Agent：我将把 client.ts 中三处调用改为 v2，运行一遍测试并回报结果，其余代码不作改动。
告知用户：A 的 Agent 称接口已于昨天改为 v2（未核实）；我正在修改三处调用。
</example>
</examples>
